Indexes

or: how to find one thing in twelve billion

The system I work on at Microsoft, Azure Resource Graph, handles more than twelve billion Azure resources a day. Reading them one by one for a single query, even at a million a second, would take over three hours. Nobody reads them. Everybody asks an index.

The short version

  • An index is the back of the book. A sorted list of values, each pointing to where its row lives. Sorted data halves the search at every step: twelve billion gets to one in about 34 steps.
  • The B-tree makes it four. Bayer and McCreight's 1970 tree is short and wide: with ~500 keys per page, four levels reach 62.5 billion entries, so one row is about four page reads, and the leaves are linked, so ranges come free.
  • The zoo. Hash (exact matches only), inverted (word → documents, for search), vector (HNSW: nearest meaning, for RAG) and LSM trees (built for non-stop writes).
  • The catch. Every index is paid for on every write (one insert, five indexes, six writes). Index what you query, need selectivity, mind column order (leftmost first), don't wrap the column in a function, and cover your hottest query.
  • At cloud scale, keep a read copy shaped for your questions, synced from change events plus a periodic full scan. The price: reads are fast but slightly late.

The 12B+ figure is from my public profile. The scan times and the 500-keys-per-page tree are illustrative arithmetic, not measurements of any real system.

12,000,000,000 rows ÷ 1,000,000 rows/s = 12,000 s ≈ 3.3 h (full scan, illustrative)
log₂(12 billion) ≈ 34 steps · 500⁴ = 62.5 billion → ~4 page reads
1 insert + 5 indexes = 6 writes

Resource Graph's own docs describe the pattern at cloud scale: when a resource changes, Azure Resource Manager notifies Resource Graph, which updates its database, and a regular full scan catches anything missed. The docs are honest about the trade: the data "isn't strongly consistent" and is "indexed with a short latency". It's the same deal a cache makes, just shaped for questions instead of lookups.

Further reading

  • Overview of Azure Resource Graph — how a whole cloud's read copy stays current, and its consistency trade.
  • Use The Index, Luke — Markus Winand's free book on SQL indexing; column order, functions and covering indexes.
  • PostgreSQL: Indexes — the costs, index types, multicolumn and expression indexes, index-only scans.
  • Azure Cosmos DB indexing policies — index-everything by default, and trimming paths for cheaper writes.
  • B-tree — Bayer and McCreight's 1970 structure behind almost every database index.
  • Log-structured merge-tree — O'Neil et al. (1996): indexing for write-heavy workloads.
  • HNSW — Malkov and Yashunin: the layered graph behind most vector search.
  • Designing Data-Intensive Applications — Kleppmann; chapter 3 compares B-trees and LSM trees.
