A Million Questions a Second

or: how I learned to stop fetching and love the Bloom filter

On Amazon's supply side, every ad that any demand source wanted to show on Amazon.com first had to pass one question: does this creative belong next to this product? Here's how we answered it over a million times a second, told mostly in pictures.

The short version, for whichever hat you're wearing

  • Precompute every answer once a day, so each request is a lookup, not a search.
  • Make "no" free with a Bloom filter, and cache on both sides of the wire.
  • Scale a Java fleet on EC2 before the peak, and don't let the garbage collector stop the world.
  • Bloom filter: about 9.6 bits per key for 1% false positives and zero false negatives, but only for the version it was built from.
  • Negative-cache empty reads, so a false positive costs one database read, once.
  • Tail latency is mostly garbage: fewer objects, flat arrays, and a collector picked for pauses.
  • Two loops, a daily batch and a request path, joined only by one versioned dataset.
  • Layers, cheapest first: the ad server's copy, then host memory, then a key-value database.
  • Fail open: a late answer is no answer, so the page serves without the relevance boost.
  • Move work out of the request. The math is cheap; moving data is not.
  • Rebuild instead of patching when inputs are messy. An idempotent daily backfill heals itself.
  • Version everything that travels together. Skew between copies is the quiet killer.
  • The calendar is the capacity plan: load-test and pre-scale before Prime Day, not during it.
  • Alarm on symptoms per host (p99, errors), with the causes one click away.
  • Ship behind end-to-end tests and an A/B test, and keep a rollback for data, not just code.
  • Relevance decides which ads get to compete. At Amazon, the highest bid doesn't win on its own.
  • The API contract was a product decision: sending the candidates with the request is what made the scale affordable.
  • The outcome: over a million requests a second at launch, proven by an A/B test, projected at $10 million a year for Amazon DSP.
01

Where we sat

Open a product page on Amazon.com and an ad server has milliseconds to fill its slots. Its candidates come from every demand source buying on Amazon's sites, and for each one it asks: does this creative belong next to this product?

"DSPs are the shoppers at the auction, and SSPs are the sellers." Amazon is both: Amazon DSP buys, Amazon Publisher Services sells for other publishers (TAM, UAM), and Publisher Technology, where I worked, builds the supply side for Amazon's own properties.

Think beer-pairing chart, Brew Miles style: the ad server brings the dish (the product) and a tray of beers (the creatives), and we say which ones go. A million pairings a second, no tasting allowed.

What I did
  • Supported the launch, end-to-end testing and A/B experiments of the Ad Relevance API for Amazon Retail. The design was the team's; I ran with a pack.
  • Root-caused a 10% request drop and fixed it through scaling policies, alarms and CI/CD.

Internal tools become public equivalents. This API's numbers are from my résumé, Amazon's wider numbers link to public write-ups, and toy or simulation means a model I ran, not production data.

03

Turn a search into a lookup

An ASIN is a product, like the trail shoe on the page. A creative is an ad that advertises one or more ASINs. Three datasets tie them together:

precompute · pseudocode
# once a day: score every (ASIN, creative) pair worth keeping
for creative in creatives_from_every_dsp():
    for product in advertises(creative):                  # creative -> ASIN
        for page, sim in similar_asins(product):          # ASIN -> ASIN
            score[page, creative] = max(score[page, creative], sim)
for new in creatives_without_history():                   # creative -> creative
    for page, s in scores_of(lookalike(new)):
        score[page, new] = s * similarity(new, lookalike(new))   # toy rule
keep(pair for pair in score if score[pair] >= threshold)  # most pairs: not stored

The move the whole system rests on is the API contract. The ad server already knew its candidates, so it sent the page's ASIN with their IDs, and a search became a few lookups:

04

Two loops, one version

Once a day, a pipeline publishes one version of every answer, everywhere. On every request, each layer tries to answer before the next, pricier one.

Animation · where a request stops
  1. Pick a journey above to send a request.
network calls: –database reads: –
hot path · pseudocode
def relevance(asin, creatives):
    snap = live_snapshot()                    # one data version for the whole request
    scores, misses = {}, []
    for c in creatives:
        key = (asin, c)
        if not snap.bloom.might_contain(key):
            scores[c] = 0                     # definitely not stored: no I/O at all
        elif (hit := snap.cache.get(key)) is not None:
            scores[c] = hit                   # hot key: host memory
        else:
            misses.append(key)
    for key, s in snap.db.batch_get(misses):  # one batched read for the rest
        snap.cache.put(key, s or 0)           # cache empty answers too
        scores[key[1]] = s or 0
    return scores

05

Make "no" free: the Bloom filter

Most pairs aren't stored, and learning that from the database is an empty read: at a million a second, a whole fleet spent learning nothing. A Bloom filter is a bouncer with a compressed guest list, a bit array and k hashes:

bloom · pseudocode
def add(key):
    for i in range(k):
        bits[(h1(key) + i * h2(key)) % m] = 1

def might_contain(key):                       # any 0 bit: definitely never added
    return all(bits[(h1(key) + i * h2(key)) % m] for i in range(k))

Any 0 bit: definitely never added. All 1s: probably. A false positive costs one wasted read; a false negative can't happen. Try it:

Playground · 24 bits, 3 hash functions

Add a few keys, then check some you never added. As the bits fill up, "maybe" gets less trustworthy, which is exactly what sizing controls.

Sorry, sorry, quick interruption

My cat is a Bloom filter. She knows instantly, with total certainty, what she does not want for dinner. "Maybe" is a longer conversation. But she has never refused something she actually wanted. No false negatives. Okay, back to the bits.

About 9.6 bits a key buys 1%, however long the key. A worked example, not our dataset.

The catch is versions. Pair tomorrow's rows with yesterday's filter and it says "definitely not" about pairs that now exist. So the filter and the rows ship together, as one version.

06

Rebuild everything, every day

Creatives, mappings and catalog data came from several DSPs and teams, on their own schedules, sometimes late or corrected. So every day the pipeline rebuilt everything from scratch: run it twice, get the same answer, and a bad day heals itself tomorrow. Press play:

Animation · the daily publish
  1. Pick a day above to run the pipeline.
publish · pseudocode
def publish(day):
    data = rebuild(creatives(day), mappings(day), catalog(day))   # from scratch
    if not looks_like(data, yesterday):       # row counts, score histogram, spot checks
        alarm(f"kept {yesterday.version}")    # yesterday keeps serving
        return
    write(data, version=day)                  # DB rows + Bloom filter + snapshot
    manifest.current = day                    # one pointer flip; everyone follows

"One pointer" is literal: a Java AtomicReference to an immutable snapshot, read once per request, so no request sees half of Monday and half of Tuesday. Treat data publishes like deploys; Sponsored Products' move to Valkey dual-wrote, shifted reads gradually and kept a rollback ready.

When the garbage collector stopped the world

The garbage collector is the only coworker who can stop the entire office to take out the trash. Ours did: under load, latency climbed because requests were being paused, worst exactly at peak. I no longer have those GC logs, so here's the anatomy rather than invented numbers. One host, one 50 ms pause; pick the load:

One host, 10,000 requests a second at full load, a 50 ms pause every 256 MB of garbage.

Two things compound: more requests make more garbage, so pauses come more often, and each backlog drains only at the host's spare capacity, so drain time grows like load ÷ (1 − load). That's "it only happens under load", explained. The playbook:

  • see it-Xlog:gc*, with pause time charted next to p99.
  • make less garbageNo boxing, reused buffers, no throwaway strings on the hot path.
  • keep big data flatA Bloom filter is one long[]; cap on-heap caches.
  • size the heap-Xms = -Xmx, a roomy young generation, -XX:+AlwaysPreTouch.
  • keep headroomThe chart above is the case against running hosts hot.
  • pick a low-pause collectorGenerational ZGC on JDK 21+, or G1 with a pause goal.

10

Nine decisions, one page

The options weighed, the one we stuck with, and why. Recommended marks what I'd pick for this workload today.

  1. What does a request carry?
    the ASIN onlyASIN + candidate creative IDsASIN + full creative data

    The ad server already had its candidates, and IDs are small. Cost: a contract tied to the ad server's IDs.

  2. When is relevance computed?
    on every requestdaily batchdaily batch + copies at the edge

    The math is cheap; fetching the data for it is not. Cost: answers up to a day old.

  3. Where do the answers live?
    database every timecentral cache clusterhost memoryall three, in layers

    The cheapest request is the one never sent. Cost: three copies to keep in agreement.

  4. How do we say "not stored"?
    ask the databaseexact hash setBloom filtercuckoo filterxor filter

    Rebuilt daily, so it never needs deletes. Cost: about 1% wasted reads.

  5. How does the data stay fresh?
    incremental updatesstreamingfull daily rebuild

    Messy upstreams; an idempotent rebuild heals itself. Cost: a full recompute every day.

  6. Where does it run?
    LambdaECS / FargateEKSEC2 Auto Scaling

    Steady, huge, latency-bound traffic; Lambda's request fees alone would be about $17,000 a day. Cost: we own capacity and patching.

  7. How does the fleet scale?
    target trackingstep scalingpredictivetarget tracking + scheduled pre-scale

    New hosts need minutes; known peaks shouldn't surprise. Cost: idle hosts before the peak.

  8. Which garbage collector?
    ParallelG1generational ZGC

    Tail latency is the product. Cost: some extra CPU and memory.

  9. How do we see a million requests a second?
    log every requestsample onlymetrics for all + sampled traces

    Know about every request; read only a few. Cost: unsampled outliers have metrics only.

The well-earned drink

Every Brew Miles trip ends with a well-earned drink. Here's this one's:

  1. Move work out of the request, and let it carry its own address.
  2. Make "no" cheap, and cache where the request starts.
  3. Version what travels together; swap one pointer.
  4. Scale before the peak, watch the worst host, and prove it with an experiment.
