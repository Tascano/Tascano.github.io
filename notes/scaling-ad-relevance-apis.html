A Million Questions a Second

or: how I learned to stop fetching and love the Bloom filter

Prefer to watch? Every animation in this post, narrated in about four and a half minutes, with captions built in. The narration is a local AI clone of my voice.

On Amazon's supply side, every ad that any demand source wanted to show on Amazon.com went through one question first: which ads belong next to this product? Here's how we answered it over a million times a second, inside 20 milliseconds, told mostly in pictures.

The short version, for whichever hat you're wearing

  • Precompute every answer once a week, so each of the ad server's 17 calls is one lookup.
  • Make "no" free with a Bloom filter, keep hot keys in memory, and answer inside 20 ms.
  • Fail small, per host, per zone, per region, and never lose a byte in the pipeline.
  • Bloom filter: about 9.6 bits per key for 1% false positives and zero false negatives, for the version it was built from.
  • Fan-out of 17 turns a rare slow call into a common slow request. Engineer the tail, not the average.
  • Tail latency is mostly garbage: fewer objects, flat arrays, a collector picked for pauses.
  • Two loops, a weekly pipeline and a call path, joined only by one versioned dataset.
  • Regions are islands: on a 20 ms path no call crosses a region, so a region fails as a unit.
  • Fail open: a late answer is no answer, so the page serves without the expansion.
  • Move work out of the request. The math is cheap; moving data is not.
  • At-least-once delivery plus idempotent writes gives exactly-once results.
  • Version everything that travels together, and publish it like a deploy.
  • The calendar is the capacity plan: load-test and pre-scale before Prime Day.
  • Page on symptoms per host, and on dead-letter queue depth; redrive is a runbook.
  • Ship behind end-to-end tests and an A/B test, with a rollback for data, not just code.
  • Relevance decides which ads get to compete. At Amazon, the highest bid doesn't win on its own.
  • The API contract was a product decision: sending the ad server a ready map is what made the scale affordable.
  • The outcome: over a million requests a second at launch, proven by an A/B test, projected at $10 million a year for Amazon DSP.

01

Where we sat

Open a product page on Amazon.com and an ad server has milliseconds to fill its slots. Its candidates come from every demand source buying on Amazon's sites, and it asks us: which ads belong next to this product?

"DSPs are the shoppers at the auction, and SSPs are the sellers." Amazon is both: Amazon DSP buys, Amazon Publisher Services sells for other publishers (TAM, UAM), and Publisher Technology, where I worked, builds the supply side for Amazon's own properties.

Think beer-pairing chart, Brew Miles style: the ad server brings the dish (the product) and one beer it likes (a creative), and we name the others that go with both. A million pairings a second, no tasting allowed.

    04

    Four mappings in, two products out

    Every week, four mappings arrived from different teams: creative ↔ creative and ASIN ↔ ASIN similarities, and creative → ASIN and ASIN → creative mappings. From them we built two things. Our answers: one DynamoDB item per (ASIN, creative), holding its ranked similar creatives. The ad server's map: ASIN → creatives, so it knows exactly which keys to ask about. One answer, built:

    precompute · pseudocode
    # once a week: build every answer the ad server can ask for
for asin, creatives in asin_to_creatives():           # ASIN -> creative
    for c in creatives:
        ranked = []
        for other, sim in similar_creatives(c):       # creative <-> creative
            fit = max(asin_sim(asin, a)               # ASIN <-> ASIN
                      for a in advertises(other))     # creative -> ASIN
            if sim * fit >= threshold:                # toy rule
                ranked.append((other, sim * fit))
        if ranked:
            items[asin, c] = top_k(ranked)            # one DynamoDB item per key
ad_map = asin_to_creatives()                          # the ad server's prefill

    That's the move the whole system rests on: the ad server never searches and never resolves a similarity. It reads its map, sends one (ASIN, creative) per call, and gets a finished list back:

    06

    Make "no" free: the Bloom filter

    Not every pair in the map has an answer: only pairs with similar creatives above the threshold get an item, and a creative that arrives mid-week has none yet. Learning that from DynamoDB is an empty read: at a million a second, a fleet spent learning nothing. A Bloom filter is a bouncer with a compressed guest list, a bit array and k hashes:

    bloom · pseudocode
    def add(key):
    for i in range(k):
        bits[(h1(key) + i * h2(key)) % m] = 1

def might_contain(key):                       # any 0 bit: definitely never added
    return all(bits[(h1(key) + i * h2(key)) % m] for i in range(k))

    Any 0 bit: definitely never added. All 1s: probably. A false positive costs one wasted read; a false negative can't happen. Try it:

    Playground · 24 bits, 3 hash functions

    Add a few keys, then check some you never added. As the bits fill up, "maybe" gets less trustworthy, which is exactly what sizing controls.

    Sorry, sorry, quick interruption

    My cat is a Bloom filter. She knows instantly, with total certainty, what she does not want for dinner. "Maybe" is a longer conversation. But she has never refused something she actually wanted. No false negatives. Okay, back to the bits.

    Memory for 100 million keys
    Bloom filter, 1% false positives
    114 MiB
    Bloom filter, 0.1% false positives
    171 MiB
    exact set, even as 8-byte hashes

    About 9.6 bits a key buys 1%, however long the key. A worked example, not our dataset.

    The catch is versions. Pair next week's items with this week's filter and it says "definitely not" about pairs that now exist. So the filter and the items ship together, as one version.

    07

    Seventeen calls, one answer

    An ad request is only as fast as the slowest of its 17 calls. That's "The Tail at Scale": fan-out turns a rare slow call into a common slow request. Drag it:

    Interactive · the slowest call sets the pace

    Fan-out multiplies load too: every ad request costs 17 calls, so capacity plans start from the fan-out, not from page views. What keeps it fast is a tiny tail per call (memory, not disk; few GC pauses) and a hard 20 ms deadline, so one slow answer is dropped rather than waited for. Partial results beat late results.     The weekly pipeline never loses a byte

    Four inputs from different teams arrive on their own schedules, sometimes late, sometimes corrected. So the pipeline is a chain of stages joined by queues: SNS fans each "dataset ready" event out to SQS queues, and workers pull from them. The queue is the contract between stages: it absorbs bursts, survives crashes, and never drops a message silently. Pick what happens:

    09

    Publish data like a deploy

    The rebuild runs from scratch every week: run it twice, get the same answer, and a bad week heals itself the next. But before anything serves, the new week has to prove it looks like the last. Press play:

    Animation · the weekly publish
    1. Pick a week above to run the publish.
    publish · pseudocode
    def publish(week):
    items, ad_map = rebuild(inputs(week))     # from scratch, every week
    if not looks_like(items, last_week):      # counts, list lengths, spot checks
        alarm(f"kept {last_week}")            # last week keeps serving
        return
    for region in waves(regions):             # one region first, then the rest
        write(region, items, bloom(items), ad_map, version=week)
        region.current = week                 # one pointer flip per region

    "One pointer" is literal: a Java AtomicReference to an immutable snapshot, read once per call, so no call ever sees half of two weeks. Publishing region by region means a bad version can't reach every region at once. Sponsored Products' move to Valkey used the same discipline for a live migration: dual writes, reads shifted gradually, a rollback ready.

    Redundancy, regions and failover

    At this volume, something is always broken: a host, an Availability Zone, a dependency, once in a long while a whole region. The pattern is to fail small, inside the smallest boundary that can contain it. Break something:

    Animation · break something
    1. Pick a failure above.

    Two principles carry it. Static stability: the spare capacity is in place before the failure, so recovery needs no scaling (AWS Builders' Library). And regional isolation: each region has its own fleet and its own copy of the data. On a 20 ms path, failover can't cross a region; a region fails as a unit, and traffic moves at the edge.

    When the garbage collector stopped the world

    The garbage collector is the only coworker who can stop the entire office to take out the trash. Ours did: under load, latency climbed because requests were being paused, worst exactly at peak, and with a 20 ms deadline a pause is a dropped answer. I no longer have those GC logs, so here's the anatomy rather than invented numbers. One host, one 50 ms pause; pick the load:

    Requests slower than 10 ms, same pause (simulation)

    One host, 10,000 requests a second at full load, a 50 ms pause every 256 MB of garbage.

    Two things compound: more requests make more garbage, so pauses come more often, and each backlog drains only at the host's spare capacity, so drain time grows like load ÷ (1 − load). That's queueing theory, and it's why "it only happens under load". The playbook:

    • see it-Xlog:gc*, with pause time charted next to p99.
    • make less garbageNo boxing, reused buffers, no throwaway strings on the hot path.
    • keep big data flatA Bloom filter is one long[]; cap on-heap caches.
    • size the heap-Xms = -Xmx, a roomy young generation, -XX:+AlwaysPreTouch.
    • keep headroomThe chart above is the case against running hosts hot.
    • pick a low-pause collectorGenerational ZGC on JDK 21+, or G1 with a pause goal.

    Back off with jitter and cap retries with a budget: in the simulation, 1,000 failures at once got 100 retries, not 2,000.

    Retries need timeouts, backoff and jitter, and a circuit breaker on the caller stops calling a failing dependency for a cooldown, then tests it with a single call. Relevance is an enhancement, not a dependency: when in doubt, the page serves without it.

    14

    Twelve decisions, one page

    The options weighed, the one we stuck with, and why. Recommended marks what I'd pick for this workload today.

    1. What does a call carry?
      the ASIN onlyASIN + one creativeASIN + full creative data

      The ad server already has the map we sent, so every call is one point lookup. Cost: a contract tied to the ad server's IDs and our weekly version.

    2. When are answers computed?
      on every callweekly batchweekly batch + a map at the ad server

      The math is cheap; fetching the data for it is not. Cost: a new creative waits up to a week for its list.

    3. Where do the answers live?
      DynamoDB every timecentral cache clusterhost memoryall three, in layers

      The cheapest call is the one never made. Cost: copies to keep in agreement.

    4. How do we say "nothing stored"?
      ask DynamoDBexact hash setBloom filtercuckoo filterxor filter

      Rebuilt weekly, so it never needs deletes. Cost: about 1% wasted reads.

    5. How do 17 calls per ad request stay fast?
      wait for all 17hedge every call20 ms deadline + partial results

      The slowest call sets the pace; a dropped answer beats a late page. Cost: now and then, fewer similar creatives.

    6. How does the data stay fresh?
      incremental updatesstreamingfull weekly rebuild

      Messy upstreams; an idempotent rebuild heals itself. Cost: a full recompute every week.

    7. How does the pipeline avoid losing data?
      cron + scriptsone big batch jobSNS → SQS stages with DLQs

      Retries, isolation and replay come built in; one bad message can't block the rest. Cost: duplicates are normal, so every write is idempotent.

    8. Where does it run?
      LambdaECS / FargateEKSEC2 Auto Scaling

      Steady, huge, latency-bound traffic; Lambda's request fees alone would be about $17,000 a day. Cost: we own capacity and patching.

    9. How does the fleet scale?
      target trackingstep scalingpredictivetarget tracking + scheduled pre-scale

      New hosts need minutes; known peaks shouldn't surprise. Cost: idle hosts before the peak.

    10. What happens when a region fails?
      fail each call over to another regionwarm standbyindependent regions, shift at the edge

      A cross-region round trip alone would blow the 20 ms budget. Cost: every region needs its own capacity and data.

    11. Which garbage collector?
      ParallelG1generational ZGC

      Tail latency is the product. Cost: some extra CPU and memory.

    12. How do we see a million calls a second?
      log every callsample onlymetrics for all + sampled traces

      Know about every call; read only a few. Cost: unsampled outliers have metrics only.

    The well-earned drink

    Every Brew Miles trip ends with a well-earned drink. Here's this one's:

    1. Move work out of the request, and hand the caller a map so every call is a lookup.
    2. Make "no" cheap, cache hot keys, and engineer the tail, because fan-out finds it.
    3. Queue between stages, write idempotently, and publish data like a deploy.
    4. Fail small and local, scale before the peak, and prove it with an experiment.
